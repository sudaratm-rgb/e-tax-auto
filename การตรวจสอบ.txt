สถานะเอกสาร (Approve เท่านั้น) และเรื่อง "เลขที่ใบเสร็จใช้ซ้ำ"  (ทดสอบ API จริง)
================================================================================
[แก้ไข 2026-07-20: เปลี่ยนจาก "ดึงทุกใบ (Approve+Draft) แล้วติดป้าย" เป็น "ดึงเฉพาะ
Approve ตั้งแต่ต้นทาง" ตามคำขอ — ใบ Draft จะไม่ถูกดึงมาแสดงในแอปนี้เลย]

แอปดึงใบเสร็จโดยส่ง status=3 (Approve) ตรงให้ GET /Receipts/list ตั้งแต่แรก จึงไม่มี
ใบ Draft หลุดเข้ามาแสดงเลย ไม่ต้องมีคอลัมน์/badge แยก Approve/Draft อีกต่อไป
(ฟังก์ชัน fetchApprovedCodes ใน lib/receipts.ts, เดิมชื่อ fetchDraftCodes)
endpoint /api/approved-receipts (ไม่มีตรวจ contact/ชำระเงิน) ก็ใช้ status=3 ตรงเช่นกัน

  ค่า status param ของ GET /Receipts/list (ยืนยันด้วย API จริง):
     1 = Draft (ร่าง)                    -- แอปนี้ไม่ดึงเลย
     3 = Approve (อนุมัติแล้ว)            -- ค่าที่แอปนี้ใช้ดึงเสมอ
     4 = Void (ยกเลิก)                   -- แอปนี้ไม่ดึงเลย

  *** สองกับดักสำคัญ (เคยทำให้ขึ้นสถานะผิด — ยังต้องระวังแม้ดึงเฉพาะ Approve แล้ว) ***

  (ก) ฟิลด์ status ในรายละเอียดใบ (GET /Receipts?code=) เชื่อถือไม่ได้
      - คืนค่า "Draft" ผิด สำหรับเลขที่เคยถูกใช้ซ้ำ ทั้งที่ของจริงอนุมัติแล้ว
      - ห้ามเอาฟิลด์นี้มาตัดสินสถานะ ให้ใช้ list status param (fetchApprovedCodes) แทนเสมอ
        แม้แต่ตอนตรวจซ้ำก่อนส่งจริงใน POST /api/send-etax (ชั้นที่ 4.5) ก็ต้องใช้วิธีนี้

  (ข) เลขที่ใบเสร็จ (code) "ใช้ซ้ำได้"
      - หลัง void ใบเก่า  PEAK ออกใบใหม่ด้วย code เดิม แต่ id ใหม่
      - GET /Receipts?code=  จึงคืนได้ "หลายเอกสาร" ต่อ 1 code (ตัว void เก่า + ตัว live ใหม่)
      - getReceipt() ใน lib/peakClient.ts เลือกตัว non-void (live) ก่อนเสมอ ไม่ใช่ตัวแรก [0]

ชั้นที่ 2 : การตรวจสอบ "ความครบถ้วนของข้อมูลลูกค้า"   (ไฟล์ validators.py)
================================================================================

ดึงข้อมูลลูกค้า (contact) จาก  GET /Contacts?code=  มาตรวจตามเงื่อนไขสรรพากร
โดยแยกตามประเภทของลูกค้า (ฟิลด์ type ที่ PEAK ส่งมาเป็นตัวเลข)


------------------------------------------------------------
2.1 เงื่อนไขที่ใช้กับลูกค้า "ทุกประเภท"
------------------------------------------------------------
  - ต้องมีข้อมูลลูกค้า (มี contact)          ถ้าไม่มี -> ไม่ผ่าน : "ไม่พบข้อมูล contact"
  - ต้องมีชื่อ (ฟิลด์ name)                  ถ้าไม่มี -> ไม่ผ่าน : "ไม่มีชื่อ contact"
  - ถ้ามีอีเมล ต้องเป็นรูปแบบที่ถูกต้อง       ถ้าผิด -> ไม่ผ่าน : "อีเมลผิดรูปแบบ: ..."
      * รองรับหลายอีเมลคั่นด้วย , ; หรือเว้นวรรค  ทุกตัวต้องถูกต้อง
      * ตัวอย่างที่ผิด: "chansakkub@gmail.com Fax"  (ส่วน "Fax" ไม่ใช่อีเมล)
      * อีเมลว่าง = ไม่ถือว่าผิด

  *การ "มี" ค่า หมายถึง ฟิลด์นั้นไม่ว่าง และไม่ใช่ช่องว่างล้วน ๆ


------------------------------------------------------------
2.2 เกณฑ์ตามประเภท (type) — แบ่ง 3 กลุ่ม
------------------------------------------------------------
  enum ของ PEAK:
    1=ห้างหุ้นส่วนจำกัด  2=บริษัทจำกัด  3=บริษัทมหาชนจำกัด  4=ร้านค้า
    5=บุคคลธรรมดา  6=คณะบุคคล  7=อื่นๆ  8=ห้างหุ้นส่วนสามัญ
    9=มูลนิธิ  10=สมาคม  11=กิจการร่วมค้า

  กลุ่ม A — บุคคลธรรมดา (type 5):
     - ที่อยู่ "อย่างน้อย 1 ฟิลด์" จาก [address, subDistrict, district, province, postCode]
       (รับที่อยู่ free-text ด้วย)
     - ไม่ต้องมี taxNumber
     ไม่ผ่าน -> "ไม่มีที่อยู่ (ต้องมีอย่างน้อย 1 ฟิลด์)"

  กลุ่ม B — บริษัท / บมจ. (type 2, 3):
     - ที่อยู่ "ครบ" : ตำบล/แขวง + อำเภอ/เขต + จังหวัด + รหัสไปรษณีย์
     - ต้องมี taxNumber
     ไม่ผ่าน -> "ที่อยู่ไม่ครบ ขาด [...]"  หรือ  "ไม่มีเลขผู้เสียภาษี"

  กลุ่ม C — นิติบุคคลอื่น (type 1,4,6,7,8,9,10,11):
     หจก. / ร้านค้า / คณะบุคคล / อื่นๆ / หสน. / มูลนิธิ / สมาคม / กิจการร่วมค้า
     - ที่อยู่ "ครบ" : ตำบล/แขวง + อำเภอ/เขต + จังหวัด + รหัสไปรษณีย์
     - ไม่ต้องมี taxNumber
     ไม่ผ่าน -> "ที่อยู่ไม่ครบ ขาด [...]"

  - branchCode (รหัสสาขา) ไม่บังคับทุกกลุ่ม
  - ตั้งกลุ่มได้ใน .env: CONTACT_TYPES_INDIVIDUAL / _FULL_TAX / _FULL_NOTAX

  [แก้ไข 2026-07-23] REQUIRE_TAXID_13DIGITS = true ใน lib/validators.ts (เปิดอยู่แล้ว
  ไม่ใช่ออปชันปิดไว้เหมือนก่อน) — "ถ้ามี taxNumber ต้องเป็น 13 หลัก" ไม่ว่ากลุ่มไหนจะ
  บังคับต้องมี taxNumber หรือไม่ก็ตาม (แม้กลุ่ม A/C ที่ปกติไม่บังคับต้องมี taxNumber เลย)
  เจอเคสจริง: RE26072917 — contact "weerapon suwanchatree" (type 5 บุคคลธรรมดา ซึ่งกลุ่มนี้
  ไม่บังคับต้องมี taxNumber) แต่มี taxNumber="0" ติดมา (ค่าขยะ ไม่ใช่เลข 13 หลักจริง)
  ถ้าไม่เช็คจุดนี้ระบบจะปล่อยผ่านเพราะกลุ่ม A ไม่สนใจ taxNumber อยู่แล้ว ทั้งที่ส่งจริงจะ
  โดน INET ตีกลับ (eTaxErrorType 19 "Contact tax number invalid data" — ดูหัวข้อ callback)
  ไม่ผ่าน -> "เลขผู้เสียภาษีไม่ใช่ 13 หลัก: X"


------------------------------------------------------------
2.3 กรณีประเภทลูกค้าที่ระบบยังไม่รู้จัก
------------------------------------------------------------
  ถ้า type ไม่อยู่ในกลุ่มใดเลย
    -> ไม่ผ่าน : "ไม่รู้จักประเภท contact (type=X)"
  เพื่อความปลอดภัย ระบบจะไม่ส่งใบที่ไม่แน่ใจประเภท


================================================================================
ชั้นที่ 3 : การตรวจสอบตอน "กดส่งจริง"   (ไฟล์ app.py + send_log.py)
================================================================================

ก่อนยิงคำสั่งส่ง  POST /Receipts/etaxinvoice  ของแต่ละใบ:

3.1 ตรวจกันส่งซ้ำอีกครั้ง (ชั้นสุดท้าย)
    - ถ้าเลขที่ใบเสร็จเคยส่งสำเร็จแล้ว (อยู่ใน log)
        -> ข้าม ไม่ส่งซ้ำ  รายงานผลเป็น "ข้าม: เคยส่งสำเร็จแล้ว"
    - ยกเว้นสั่ง force = true (บังคับส่งซ้ำ) จึงจะส่งอีกครั้ง

3.2 ส่งคำสั่งไป PEAK พร้อมพารามิเตอร์:
    - code             = เลขที่ใบเสร็จ
    - etaxConnectType  = 2  (ช่องทาง INET — ทดสอบยืนยันแล้วว่าค่านี้ถูกต้อง)
    - isUpdateDocument = 0  (ไม่อัปเดตเอกสารก่อนส่ง)

3.3 บันทึกผล "ทุกครั้ง" ลงไฟล์ sent_log.jsonl  (ทั้งสำเร็จและล้มเหลว)
    แต่ละบรรทัดเก็บ:
    - timestamp      = เวลาที่ส่ง
    - code           = เลขที่ใบเสร็จ
    - success        = สำเร็จหรือไม่ (true/false)
    - resCode        = รหัสตอบกลับจาก PEAK (200 = สำเร็จ)
    - resDesc        = ข้อความอธิบายผล

3.4 สรุปผลรวมหลังส่ง:
    - ส่งสำเร็จกี่ใบ / ล้มเหลวกี่ใบ / ข้ามกี่ใบ
    - หลังส่งเสร็จ ระบบ refresh ตารางอัตโนมัติเพื่ออัปเดตป้าย "ส่งแล้ว"

ชั้นที่ 4 (เพิ่มใหม่) : การตรวจสอบ "สถานะเอกสาร (Approve)" + "สถานะการชำระเงิน"
                        [เพิ่มหลังย้ายไป Next.js]
================================================================================
กติกาธุรกิจ: ส่ง e-Tax ได้เฉพาะใบเสร็จที่ "อนุมัติแล้ว (Approve)" เท่านั้น — ข้อนี้
ตรวจสอบกับ Document ของ PEAK แล้ว (POST /Receipts/etaxinvoice ที่
https://developers.peakaccount.com/reference/post_api-v1-receipts-etaxinvoice) ว่า
"ไม่มีการบังคับ/เอกสารระบุไว้จาก PEAK เอง" — เป็นกติกาธุรกิจของระบบนี้ที่ต้องบังคับเอง
ไม่ใช่สิ่งที่ PEAK API เช็คให้อัตโนมัติ

ไฟล์ที่เกี่ยวข้อง: lib/peakClient.ts (getReceipt) + lib/receipts.ts (buildRow,
fetchApprovedCodes) + app/api/send-etax/route.ts

4.1 เช็คอนุมัติแล้วหรือยัง (Approve) — เช็คฟรี ไม่ต้องเรียก API เพิ่ม (ชั้นที่ 1)
    [แก้ไข 2026-07-20: เดิมดึงทุกใบมาแล้วติดป้าย Draft/Approve — ตอนนี้ /api/fetch ดึง
    เฉพาะ status=3 (Approve) ตั้งแต่ต้นทางแล้ว (ดูหัวข้อ "สถานะเอกสาร" ด้านบน) ใบ Draft
    จึงไม่มีทางหลุดเข้ามาถึงขั้นตอนนี้เลย docStatus ของทุกแถวจึงเป็น "Approve" เสมอ
    ไม่ต้องมี logic ตรวจ/ตีเป็น valid=false เพราะ Draft อีกต่อไปในชั้นนี้]

4.2 การบังคับใช้ซ้ำตอนกดส่งจริง (สำคัญที่สุด — แหล่งความจริงเดียว)
    POST /api/send-etax ตรวจ "อนุมัติแล้วหรือยัง" ซ้ำ "ทุกครั้ง" ก่อนยิงส่งจริงแต่ละใบ
    ไม่พึ่งพาผลตรวจจาก /api/fetch ฝั่ง client เพียงอย่างเดียว เพราะ:
      - ข้อมูลอาจเก่า (เวลาผ่านไปนานหลังโหลดตาราง เอกสารอาจเพิ่งถูกอนุมัติหรือยกเลิก
        การอนุมัติ)
      - อาจมีคนเรียก POST /api/send-etax ตรงจาก API โดยไม่ผ่านหน้าเว็บ/ไม่ผ่าน /api/fetch
        (ซึ่งตอนนี้ดึงเฉพาะ Approve อยู่แล้ว แต่ endpoint นี้ยังต้องเป็นแหล่งความจริงเอง)
    ใบที่ยังไม่อนุมัติ ณ ตอนกดส่งจริง -> ข้าม ไม่ยิงคำขอไป PEAK เลย
    รายงานผลเป็น "ข้าม: เอกสารยังไม่อนุมัติ (Draft)"  (เหมือนกลไกกันส่งซ้ำในชั้นที่ 3.1)

    *** สำคัญ: เช็คอนุมัติซ้ำที่นี่ "ห้ามใช้" ฟิลด์ status ของ GET /Receipts?code=
    ตรง ๆ *** เพราะฟิลด์นี้เชื่อถือไม่ได้สำหรับเลขที่ใบเสร็จใช้ซ้ำ (ดูกับดัก (ก) ด้านบน
    — คืน "Draft" ผิดทั้งที่อนุมัติแล้วจริง) ถ้าใช้ตัดสินจะบล็อกใบที่อนุมัติแล้วผิด ๆ ได้
    ต้องใช้ list status param แทนเสมอ: เรียก fetchApprovedCodes (status=3) ต่อวันที่ออกใบ
    แล้วเช็คว่า code "อยู่ใน" ชุดที่อนุมัติแล้วหรือไม่ (มี cache ต่อวันกันยิงซ้ำเวลามีหลาย
    ใบวันเดียวกัน) — ตรงกว่าการเช็ค "ไม่อยู่ในชุด Draft" แบบเดิม เพราะกันเคส void(4)
    หลุดผ่านไปด้วย (เอกสาร void ไม่อยู่ทั้งในชุด Draft และ Approve)

4.3 [ถอดออกแล้ว 2026-07-22] เคยเช็คสถานะชำระเงิน (Paid) ด้วย — remainAmount เชื่อถือไม่ได้
    เดิมมีกติกาว่าต้อง "ชำระเงินครบแล้ว" (remainAmount <= 0 จาก GET /Receipts?code=)
    ก่อนส่ง e-Tax ได้เช่นกัน — ถอดออกแล้ว เพราะตรวจสอบพบ 2 เคสติดกัน:
      - RE26072241 (issuedDate 20260716): มี paidPayments[] บันทึกชำระครบ 9,912.48 บาท
        ตรงวันที่ออกใบเป๊ะ (paymentDate 20260716) แต่ remainAmount ยังโชว์ 9,912.48
        (เต็มจำนวน ไม่ลดเลย)
      - RE26072955 (issuedDate 20260720): มี paidPayments[] บันทึกชำระครบ 2,600.10 บาท
        ตรงวันที่ออกใบเป๊ะ (paymentDate 20260720) แต่ remainAmount ยังโชว์ 2,600.10
        (เต็มจำนวน ไม่ลดเลย)
    ทั้งสองเคส "จ่ายวันเดียวกับที่ออกใบ" แต่ remainAmount ไม่อัปเดตสะท้อนการชำระเลย —
    สรุปว่า remainAmount ไม่น่าเชื่อถือพอจะใช้เป็นเงื่อนไขบังคับส่ง (อาจเป็นความหน่วง
    ของ PEAK เอง ไม่ใช่ real-time reconcile) จึงถอดเงื่อนไขนี้ออกทั้งจาก /api/fetch
    (buildRow) และ /api/send-etax — ฟังก์ชัน isPaidReceipt/applyPaymentGate ถูกลบแล้ว

    ถ้าจะกลับมาใช้ในอนาคต ควรพิจารณาเช็ค paidPayments[] ประกอบด้วย (มี record + ยอดรวม
    ครบ netAmount ก็ถือว่าจ่ายแล้ว) แทนที่จะเชื่อ remainAmount เพียงอย่างเดียว

จะรู้ได้อย่างไรว่า "ใบไหนถูกส่งไปแล้ว"  (ทั้งจาก UI และจากการเรียก API)
================================================================================

แหล่งความจริงเดียว = ไฟล์ sent_log.jsonl  ฝั่งเซิร์ฟเวอร์
ไม่ว่าจะกดส่งจาก "หน้าเว็บ" หรือเรียก "API" ตรง ทุกการส่งวิ่งผ่าน endpoint
เดียวกัน (POST /api/send-etax) จึงถูกบันทึกลง log เดียวกันเสมอ
ดังนั้น "ใครก็ตาม" สามารถถามสถานะการส่งได้ผ่าน API ต่อไปนี้:

  1) GET /api/sent-codes
     -> คืน code ทั้งหมดที่เคยส่งสำเร็จแล้ว
        ตัวอย่าง: {"count":2,"codes":["RE26062028","RE26062227"]}

  2) GET /api/sent-status?codes=RE26062227,RE26062128
     -> เช็คทีละหลายใบ คืนทั้ง map และแยกกลุ่ม
        {"status":{"RE26062227":true,"RE26062128":false},
         "sent":["RE26062227"], "notSent":["RE26062128"]}

  3) GET /api/sent-log?limit=200
     -> ประวัติการส่งทั้งหมด (เวลา, code, success, resCode, resDesc)

  4) POST /api/fetch  (ดึงใบเสร็จตามวันที่)
     -> แต่ละแถวมีฟิลด์ alreadySent: true/false ติดมาให้อยู่แล้ว

หมายเหตุสำคัญ:
  - การกันส่งซ้ำใช้ log นี้เป็นตัวตัดสิน  ไม่ได้ใช้ taxStatus ของ PEAK
    (ยืนยันด้วย API จริง: taxStatus = 0 เท่ากันหมดทั้งใบที่ส่งแล้ว/ยังไม่ส่ง — ใช้ไม่ได้)
  - *** ข้อจำกัด: ใบที่กดส่ง e-Tax เองผ่าน PEAK UI จะไม่อยู่ใน log นี้ ***
    และ "ตรวจจับอัตโนมัติไม่ได้" เพราะ PEAK API ไม่มีฟิลด์/endpoint บอกสถานะ e-Tax เลย
    -> แนะนำให้ส่งผ่านแอปนี้ช่องทางเดียว เพื่อให้ log ครบถ้วน
  - resCode 200 = PEAK "รับคำขอ" แล้ว ไม่ได้การันตีว่า INET ออกใบสำเร็จ 100%
    การคัดกรองที่อยู่/อีเมลให้ครบถูกต้องตั้งแต่ชั้นที่ 2 จึงช่วยลดเคสล้มเหลวปลายทาง
    (ถ้า deploy มี public URL: ใช้ callback url ตอนส่ง เพื่อรับผลจริงจาก INET กลับมาบันทึก)


================================================================================
ผลออกใบจริงแบบ async + callback  (resCode 200 ตอนส่ง ≠ ออกใบสำเร็จ)
================================================================================

การส่ง e-Tax เป็น asynchronous:
  - ตอนยิง POST /Receipts/etaxinvoice  ได้ resCode 200 = PEAK "รับคำขอ" เท่านั้น
  - การออกใบจริงผ่าน INET เกิดทีหลัง และ "อาจล้มเหลว" โดย PEAK API ไม่บอกผล
  - รู้ผลจริงได้ทางเดียว = ตั้ง callback URL ให้ INET ยิงผลกลับมา (ทดสอบ API จริงแล้ว)

วิธีผูกผล callback กับใบ (สำคัญ):
  - ระบบส่ง keyReference = code ไปทุกครั้ง
  - PEAK ยิงผลกลับมาใน HTTP header ชื่อ "Key-Reference"  (ไม่ใช่ใน body!)
  - body ของ callback เช่น:
      {"resCode":"303","resDesc":"Send E-Tax Invoice Incomplete",
       "resError":{"eTaxErrorType":19,"message":"Contact tax number invalid data."}}

การบันทึกและตัดสินสถานะ:
  - ผล callback บันทึกทับสถานะเดิม (phase=callback)
      resCode 200  -> ออกใบสำเร็จจริง (issued)
      resCode อื่น -> ล้มเหลว (failed)  เช่น 303
  - sent_codes() ใช้ "entry ล่าสุดต่อ code" -> ใบที่ INET ตีกลับจะไม่ถูกนับว่าส่งแล้ว
    และ "ส่งซ้ำได้" หลังแก้ข้อมูล (ไม่ถูกบล็อกถาวรเหมือนเดิม)

สถานะต่อใบ  GET /api/etax-status?codes=A,B,C :
  pending = รับคำขอแล้ว (200) รอ INET ยิงผลกลับ
  issued  = callback resCode 200 (ออกใบสำเร็จจริง)
  failed  = callback ≠ 200 (เช่น 303) หรือส่งล้มเหลวตั้งแต่ยิง

หน้าเว็บ (index.html):
  - หลังกดส่ง ขึ้น "กำลังรอผลออกใบจริงจาก INET..." แล้ว poll /api/etax-status ทุก 3 วิ
  - แจ้งผลต่อใบ "ออกใบสำเร็จ X / ส่งไม่ผ่าน Y" พร้อมเหตุผล (เช่น eTaxErrorType)

eTaxErrorType ที่เจอจริง (อ้างอิง):
   7 = Contact email invalid length   (อีเมลผิดความยาว)
  19 = Contact tax number invalid data (เลขผู้เสียภาษีไม่ถูกต้อง/ไม่มี เช่น บุคคลธรรมดา)

*** ข้อควรระวัง: callback ต้องวิ่งกลับมาถึงแอปได้ ***
  - ต้อง deploy ให้มี public URL  แล้วตั้ง ETAX_CALLBACK_URL ชี้มาที่ /api/etax-callback
  - บน localhost callback ไปไม่ถึง -> หน้าเว็บจะค้าง pending จนหมดเวลา
  - ทดสอบดู payload จริงได้ด้วย webhook.site (ใช้ "endpoint URL" ไม่ใช่ลิงก์หน้า view)


================================================================================
การยืนยันตัวตนกับ PEAK API  (ไม่ใช่ "การตรวจสอบใบเสร็จ" แต่เกี่ยวข้องทุก request)
================================================================================

ทุกคำขอที่ส่งไป PEAK ต้องแนบ 4  header (ระบบเซ็นให้อัตโนมัติ):
  - Time-Stamp      = เวลาปัจจุบันแบบ UTC  รูปแบบ yyyyMMddHHmmss
                      (สำคัญ: ต้องเป็น UTC ไม่ใช่เวลาเครื่อง มิฉะนั้น PEAK ตอบ resCode 400)
  - Time-Signature  = HMAC-SHA1 ของ Time-Stamp โดยใช้ connectId เป็น secret (แบบ hex)
  - User-Token      = token จาก PEAK
  - Client-Token    = token ที่ "หมดอายุได้"

Client-Token หมดอายุ -> refresh อัตโนมัติ:
  - เมื่อหมดอายุ PEAK ตอบ resCode 600 "Invalid Client Token"
  - ระบบจะ mint token ใหม่เองผ่าน POST /api/v1/ClientToken (ใช้ connectId + connectKey)
    แล้วลอง request เดิมซ้ำอัตโนมัติ (มี lock กันการ refresh ซ้ำตอนยิงขนาน)
  - connectKey = ค่า Password จากหน้า PEAK API settings

นอกจากนี้ระบบยังตรวจค่า resCode ที่ PEAK ส่งกลับทุกครั้ง:
  - resCode = "200"  -> สำเร็จ
  - resCode อื่น     -> ถือว่าผิดพลาด พร้อมแสดง resDesc ให้ทราบสาเหตุ

สรุปสั้น: ระบบตรวจอะไรบ้าง
================================================================================
  1. ใบนี้เคยส่ง e-Tax ไปแล้วหรือยัง          (กันส่งซ้ำ ใช้ log ฝั่งเรา)
  2. มีข้อมูลลูกค้า และมีชื่อลูกค้าไหม
  3. ประเภทลูกค้าเป็นที่รู้จักไหม (ไม่รู้จัก = ไม่ส่ง)
  4. ตามกลุ่ม type:
       - 5 บุคคลธรรมดา: ที่อยู่ ≥1 ฟิลด์
       - 2,3 บริษัท/บมจ.: ที่อยู่ครบ 4 ฟิลด์ + ต้องมี taxid
       - อื่นๆ (1,4,6,7,8,9,10,11): ที่อยู่ครบ 4 ฟิลด์ ไม่ต้อง taxid
  5. อีเมล (ถ้ามี) รูปแบบถูกต้องไหม           (ผิด = ไม่ผ่าน)
  5.5. taxNumber (ถ้ามีค่า ไม่ว่ากลุ่มไหน) ต้องเป็นเลข 13 หลัก (ผิด = ไม่ผ่าน)
       เช่น taxNumber="0" ของบุคคลธรรมดา (กลุ่มที่ไม่บังคับต้องมี) ก็ไม่ผ่านเช่นกัน
  6. branchCode ไม่บังคับทุกกลุ่ม
  7. ตอนกดส่ง: ตรวจกันส่งซ้ำอีกครั้ง + บันทึกผลทุกใบ
  8. อนุมัติเอกสารแล้วหรือยัง (Approve ไม่ใช่ Draft) — ตอนดึงรายการ (/api/fetch) รับประกัน
     แล้วโดยดึงเฉพาะ status=3 มาตั้งแต่ต้น (ใบ Draft ไม่ถูกดึงมาแสดงเลย) ส่วนตอนกดส่งจริง
     ตรวจซ้ำด้วย list status param (fetchApprovedCodes) เสมอ ไม่ใช้ฟิลด์ status รายใบ
     (ข้อนี้ไม่ใช่กติกาที่ PEAK เอกสารไว้ — เป็นกติกาธุรกิจของระบบนี้เอง POST /api/send-etax
     จึงต้องตรวจซ้ำเสมอก่อนยิงจริง ไม่พึ่งผลจาก client อย่างเดียว — ดูชั้นที่ 4 ด้านบน)
  9. [ถอดออกแล้ว 2026-07-22] เคยเช็คชำระเงินครบหรือยัง (remainAmount <= 0) — พบว่า

  + ดึงเฉพาะใบ Approve ตั้งแต่ต้นทาง (ใช้ list status param ไม่ใช่ฟิลด์ status รายใบ)
    + ระวังเลขที่ใบเสร็จใช้ซ้ำได้ -> getReceipt() เลือกตัว non-void; ดู /api/approved-receipts
